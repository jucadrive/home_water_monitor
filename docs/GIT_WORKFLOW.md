# Git 작업 전략

## 브랜치
- `main`은 검증된 변경을 통합하는 기준 브랜치다.
- 작업은 `codex/<작업명>`의 짧은 수명 브랜치에서 진행한다.
- 하네스 최초 체크포인트는 `codex/harness-bootstrap`을 사용한다.
- 새 작업 전 현재 브랜치·작업 트리·기준 커밋을 확인한다.
- 미커밋 변경이 있으면 소유와 범위를 확인하고 임의 stash·삭제·덮어쓰기를 하지 않는다.
- 작업이 끝나면 해당 브랜치에서 검증하고 PR로 main에 통합한다.
- PR 생성과 main 병합은 자동 수행하지 않고 사용자 승인을 받는다.
- 브랜치 보호·필수 CI 검사는 별도 설정이며 이 문서만으로 강제되지 않는다.

## 커밋과 푸시 승인
- AI가 변경을 검토하고 커밋·푸시를 수행하되 각 작업의 명시적 승인을 받는다.
- 사용자가 현재 변경을 커밋하라고 직접 지시하면 해당 범위의 커밋 승인이다.
- 커밋 승인은 푸시·PR 생성·병합 승인으로 확장하지 않는다.
- 승인 요청 전에 변경 파일·검증 결과·브랜치·커밋 메시지를 준비한다.
- 푸시는 대상 remote·브랜치·커밋을 제시하고 승인 후 수행한다.
- 사용자가 범위를 명시해 커밋과 푸시를 함께 승인하면 중복 승인 요청을 하지 않는다.
- 승인된 변경 파일만 명시적으로 stage하며 다른 작업·비밀정보·빌드 결과는 제외한다.
- 커밋 후 status와 커밋 내용을 확인하고 푸시 후 원격 반영을 확인한다.
- force push, reset --hard, clean, 원격 브랜치 삭제는 별도 승인 없이 실행하지 않는다.

## 검증과 CI
- 코드 변경에 필요한 검증은 AGENTS.md와 작업 명세를 따른다.
- 이미 성공한 검증 이후 문서만 변경됐다면 diff·문서 검토를 수행한다.
- 푸시 후 해당 커밋 SHA의 GitHub Actions 결과를 확인한다.
- 원격 조회 권한이나 도구가 없으면 Actions 링크와 확인 절차를 사용자에게 제공한다.
- 원격 CI 성공 확인 전 로컬 성공을 원격 성공으로 보고하지 않는다.
- 실패 시 로그를 분석하고 승인 범위 안에서 수정한다. 추가 커밋·푸시는 다시 승인받는다.
